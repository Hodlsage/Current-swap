1. Engagement Overview

BlockHaus.Company was engaged to perform a security assessment of the Current (CRNT) token contract, a custom atomic ERC-20 token serving as the dollar instrument for the Current Network platform. The assessment combined AI-enhanced automated source analysis with human engineering review.

CRNT is an intentionally atomic token: decimals() returns 0, making one CRNT a single indivisible unit pegged to one US dollar. The contract supports role-gated minting and burning (to support gold-backed issuance via the platform's redemption vault), an emergency pause, per-address freezing for compliance, and a two-step ownership transfer.

1.1 Scope

In scope: the single file Current.sol (contract Current). Out of scope: the redemption vault, the front-end application, off-chain price feeds, deployment scripts, and key management procedures, except where they affect reasoning about the token contract.

4. Detailed Findings

LOW-01   Administrative control (mitigated by multisig governance)

Description. The owner and authorized roles can mint tokens, pause all transfers, and freeze individual addresses. In isolation, a single compromised owner key could mint supply or freeze users.

Assessment. These powers are intentional and standard for a regulated-style, asset-backed dollar instrument (comparable controls exist in major fiat-backed stablecoins). The deployment architecture mitigates the single-key risk: privileged roles (owner, and the minter/pauser roles) are assigned to an external M-of-N multi-signature wallet rather than an individual key, so no single party can unilaterally execute a privileged action. The contract's role design supports multiple independent role-holders, and every privileged action emits an event for monitoring. This is a documented, governed design trade-off, not a defect.

Recommendation. Confirm at sign-off that owner and all minter/pauser roles are held by the production multi-signature wallet(s); record the signer set and threshold; consider adding a timelock for the most sensitive actions; publish the role-holder addresses; and monitor the emitted events.

LOW-02   Freeze can trap balances

Description. A frozen address can neither send nor receive, which by design can immobilize a user's balance indefinitely while frozen.

Assessment. This is the intended compliance behavior (theft response, court order, sanctions). It is reversible by a pauser via setFrozen(account, false).

Recommendation. Maintain an off-chain governance policy describing the criteria and approval process for freezing, and log decisions.

INFO-01   SafeMath intentionally omitted

Solidity 0.8.24 performs checked arithmetic at the language level; explicit SafeMath would be redundant. unchecked blocks are used only where a preceding require mathematically guarantees no overflow/underflow. Verified correct in each instance.

INFO-02   Infinite-allowance pattern

transferFrom / burnFrom do not decrement an allowance set to type(uint256).max. This is a widely adopted gas optimization and is documented in code.

INFO-03   No native-asset handling

The contract has no receive/fallback and never custodies BNB, removing an entire class of value-handling risk. Confirmed appropriate.

INFO-04   Pinned compiler version

The pragma is pinned to an exact version (0.8.24) rather than a floating range, which is best practice for reproducible, audited deployments.

5.1 Test Evidence

A functional and security test suite of 41 assertions was executed against the contract on a local EVM. All 41 assertions passed, covering metadata/atomicity, role enforcement, mint/burn access control, transfer and allowance semantics (including the infinite-allowance path), pause and freeze enforcement, the two-step ownership flow, and zero-address / confirmation guards. The deployed bytecode is 5,790 bytes, well within the 24,576-byte contract size limit.

6. Conclusion

Within the audited scope, the Current contract is well-structured, follows current Solidity security practices, and contains no critical, high, or medium-severity vulnerabilities. The administrative powers it exposes are intentional and appropriate for a regulated-style dollar instrument, and are accompanied by complete event logging. The two low-severity items are documented design trade-offs.

BlockHaus considers the contract suitable for the planned testnet validation. The administrative powers it exposes are governed by an external M-of-N multi-signature wallet in the production deployment, removing single-key control. Prior to a mainnet deployment carrying material value, BlockHaus recommends: (1) confirming all privileged roles are held by the production multisig (and ideally adding a timelock for the most sensitive actions); (2) an additional independent third-party audit; and (3) a public bug-bounty program.
